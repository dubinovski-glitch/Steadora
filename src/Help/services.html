Feature Services

The Feature layer sits between the API controllers and the Infrastructure repositories. Each feature is a self-contained project that can be toggled on or off via appsettings.json without breaking the rest of the solution.

Feature flag pattern

In Program.cs, each feature's service is only registered when its flag is true. When disabled, a no-op stub is registered instead, so controllers never receive a null injection.

if (config["Features:Incidents"] == "true")
    builder.Services.AddScoped<IIncidentService, IncidentService>();
else
    builder.Services.AddScoped<IIncidentService, NoOpIncidentService>();

IncidentService · Features.Incidents/IncidentService.cs

The busiest feature service. Provides the full lifecycle of an incident — creation, status transitions, assignment, priority escalation, problem linking, and bulk close. Delegates all data access to IncidentRepository.

Logging
Logs to logs/Incidents.log via a dedicated log4net appender. Meaningful events logged at INFO: incident created (with title + ID), bulk close (with count). Errors logged at ERROR with full exception stack trace.

Dependency

Constructor-injected: IIncidentRepository repo, ILog log

Notable behaviour

  • GetQueueAsync — passes the IncidentFilter directly to the repo; the service layer adds no extra filtering logic.
  • BulkCloseAsync — iterates the ID list and calls repo.SoftDeleteAsync per item; logs "Bulk-closed N incidents" at INFO when done.
  • CreateAsync — logs "Created incident #{id}: {title}" at INFO after the repo returns the new ID.

ProblemService · Features.Problems/ProblemService.cs

Thin orchestration layer over ProblemRepository. No additional business rules beyond logging and error re-throw.

Logs to logs/Problems.log.

ChangeService · Features.Changes/ChangeService.cs

Delegates to ChangeRepository. The VoteAsync method logs "User {extId} voted {voteCode} on change #{id}" at INFO — useful for change approval auditing in log files. Logs to logs/Changes.log.

NotificationService · Features.Notifications/NotificationService.cs

Delegates to ActivityRepository. PostCommentAsync is the most important method: it calls the itil.usp_AddComment stored procedure which in turn fans out Notification rows to all watchers. The service logs each new comment at INFO. Logs to logs/Notifications.log.

SignalR integration point
After posting a comment, the NotificationsController can push a real-time signal via NotificationHub. The current implementation leaves this as a direct call site; a future refactor could move the hub push into the service.

SlaService · Features.Sla/SlaService.cs

Wraps SlaRepository with error handling. All four analytics methods delegate directly to the repo. Logs to logs/Sla.log.

SlaBackgroundService · Features.Sla/SlaBackgroundService.cs

An ASP.NET Core IHostedService registered in Program.cs. Runs continuously in the background and evaluates SLA breaches on a fixed interval.

Lifecycle

// Simplified
protected override async Task ExecuteAsync(CancellationToken stopping)
{
    while (!stopping.IsCancellationRequested)
    {
        await scope.ServiceProvider
            .GetRequiredService<ISlaRepository>()
            .EvaluateBreachesAsync();
        await Task.Delay(TimeSpan.FromSeconds(60), stopping);
    }
}
Scoped service in a singleton host
IHostedService is registered as Singleton, but ISlaRepository is Scoped. The service creates a new DI scope per iteration via IServiceScopeFactory to avoid capturing a stale DbConnection.

What the stored procedure does

The reporting.usp_EvaluateSlaBreaches procedure:

  1. Creates #breached and #warned temp tables
  2. Calculates elapsed minutes for all open, non-deleted incidents using business-hours logic
  3. Updates SlaBreachedAt where elapsed > target
  4. Updates SlaWarnedAt where elapsed > 75% of target
  5. Recalculates SlaPercent for all open incidents

Logs to logs/Sla.log. Any errors are logged at ERROR and swallowed (so the loop continues on the next tick even if one evaluation fails).
